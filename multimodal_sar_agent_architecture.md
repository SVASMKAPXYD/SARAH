# Multimodal Search-and-Rescue Agent — Architecture Specification

## 1. Objective

Build a simulated search-and-rescue rover in a Three.js 3D terrain. The rover must explore an initially unknown environment, use aligned RGB, thermal, and LiDAR-like geometric observations to locate a missing person, confirm the candidate with multi-modal evidence, reach the person, and return to base through a known safe route.

**Core rule:** Gemini is a high-level multimodal decision agent. Deterministic local code owns geometry, mapping, collision safety, exact path execution, and world truth.

```text
RGB + thermal + local geometry + topological memory
                     ↓
              Gemini decision
                     ↓
       choose one legal graph edge/frontier
                     ↓
 local planner/executor traverses detailed route
                     ↓
  render/rescan/update graph/repeat
```

## 2. Scope and Assumptions

- Use a stylized Three.js environment: forest/terrain, obstacles, paths, hazards, base, survivor, and optional warm decoys.
- The simulator holds ground truth. Gemini never receives the complete map or survivor coordinates.
- The rover has a first-person RGB camera, an aligned false-color thermal camera, and simulated LiDAR generated by Three.js raycasts.
- Navigation uses a **topometric graph**: a sparse topological graph with small metric metadata on nodes and edges.
- The rover makes one Gemini decision per meaningful navigation event, not every render/physics frame.
- This is an agentic simulation, not online RL or continuous low-level robotic control.

## 3. Responsibilities

| Component | Responsibilities | Must not do |
|---|---|---|
| Three.js world | Terrain, obstacles, survivor/decoy placement, camera rendering, collision/raycast truth, animation | Reveal hidden map/survivor location to Gemini |
| Local perception/mapping | LiDAR rays, legal movements, graph updates, frontier discovery, evidence persistence, safe paths | Ask Gemini to maintain exact geometry |
| Gemini | Jointly interpret RGB + thermal + compact geometry/memory; choose a safe candidate route/action; assess survivor evidence; provide one short rationale | Control physics, maintain full map, invent unsafe moves |
| Local executor | Validate Gemini choice, follow edge polyline, stop/interrupt on meaningful events | Trust invalid/unlisted model outputs |
| UI | Third-person scene, RGB/thermal panels, graph/minimap, agent trace, mission state | Treat Gemini rationale as ground truth |

## 4. Mapping: Sparse Topometric Graph

### 4.1 Why this representation

A dense occupancy grid stores many cells/voxels and is unnecessary for the hackathon simulation. Store only meaningful places and verified connectivity. Immediate collision geometry comes from live Three.js raycasts.

```text
Global memory: topological graph of places/paths
Local safety: current raycast geometry and collision checks
```

### 4.2 Node definition

A node is a meaningful place: base, intersection, dead end, major turn, useful camera viewpoint, evidence location, survivor location, or extraction point.

Create a node when at least one condition holds:

- First/deployment location or base
- Two or more safe outgoing routes are available
- A corridor ends or reaches a dead end
- Route heading changes materially (for example >30 degrees)
- A new thermal/RGB clue crosses an evidence threshold
- It is more than 3–5 m from the nearest existing graph node
- It is task-important: candidate, survivor, extraction, blocked-route point

Do not create a node at every meter.

```ts
type TopoNode = {
  id: string;
  x: number;
  z: number;
  headingDeg: number;
  kind: "BASE" | "JUNCTION" | "VIEWPOINT" | "DEAD_END" | "EVIDENCE" | "SURVIVOR" | "EXTRACTION";
  visited: boolean;
  observationCount: number;
  thermalScore: number;       // 0..1, locally accumulated
  rgbPersonScore: number;     // 0..1, locally accumulated
  evidenceFrames: number;     // consecutive/persistent observations
  note?: string;
};
```

### 4.3 Edge definition

A known edge is a verified traversable route between nodes. It may contain many local waypoints/turns but appears as **one topological step** to Gemini.

```ts
type TopoEdge = {
  id: string;
  from: string;
  to: string;
  lengthM: number;
  bearingDeg: number;
  safe: boolean;
  traversed: boolean;
  minClearanceM: number;
  terrain: "TRAIL" | "FOREST" | "SLOPE" | "BRIDGE";
  hazardCost: number;
  polyline: Array<{ x: number; z: number }>;
};
```

Example physical route:

```text
A → forward 5 m → right curve → forward 8 m → left curve → forward 4 m → B
```

Stored topologically:

```text
A ── E17: safe eastern trail, 17 m ── B
```

### 4.4 Frontier definition

A frontier is a safe-looking, observed direction from a known node that leads into unknown terrain.

```ts
type Frontier = {
  id: string;
  fromNode: string;
  bearingDeg: number;
  estimatedDistanceM: number;
  geometry: "CLEAR" | "NARROW" | "UNCERTAIN";
  thermalAlignment: number;      // 0..1
  expectedInformationGain: number; // 0..1
  status: "UNEXPLORED" | "TRAVERSED" | "BLOCKED";
};
```

## 5. Perception and Map Update

At each arrival node or meaningful interruption:

1. Render RGB image from rover camera.
2. Render aligned thermal image from a second camera/material pass.
3. Cast a fan of rays (for example 7–9 rays over ±60 degrees).
4. Convert ray hits to local traversability: clear, blocked, hazardous, narrow.
5. Mark current node visited; add/update outgoing edges/frontiers.
6. Attach local thermal/RGB evidence to current node.
7. Merge/compress unimportant straight-corridor points.
8. Recompute routes to base and candidate frontiers.
9. Build a compact Gemini observation packet.

Ray/world conversion if needed:

\[
x_{world}=x_r+d\cos(\theta+\phi), \qquad z_{world}=z_r+d\sin(\theta+\phi)
\]

where \((x_r,z_r)\) is rover pose, \(\theta\) heading, \(\phi\) ray offset, and \(d\) ray range.

## 6. Navigation Hierarchy

| Layer | Decision unit | Owner |
|---|---|---|
| Mission | Search → investigate → confirm → rescue → extract | Local state machine + Gemini intent |
| Topological | Select next known edge or frontier | Gemini |
| Local metric traversal | Follow stored polyline; make small turns/motions; collision check | Deterministic code |
| Rendering/physics | Frame-level position/orientation changes | Three.js loop |

**One Gemini step = choose a next meaningful route, not a wheel command or 0.5 m movement.**

### Traversal protocol

```text
Gemini selects E17 or F4
      ↓
Local code validates selection
      ↓
For known edge: follow stored E17.polyline to destination node
For frontier: move through corridor until a new junction/dead end/evidence/hazard
      ↓
Create/update graph state
      ↓
Query Gemini again
```

Interrupt edge traversal and query Gemini early only if:

- Strong new thermal/RGB evidence appears
- Path becomes blocked/unsafe
- A new branch/intersection is discovered
- Localization/path execution fails
- A meaningful hazard or survivor clue is encountered

## 7. Search and Rescue State Machine

```text
SEARCH → INVESTIGATE → CONFIRM → RESCUE → EXTRACT → COMPLETE
                   ↘ SEARCH (false lead)
```

### SEARCH

- Generate top 3–5 reachable frontiers from graph state.
- Score locally for safety, travel cost, information gain, and thermal alignment.
- Gemini chooses among candidate routes using RGB/thermal context and mission state.

Example local candidate score:

\[
S(f)=w_I I(f)+w_T T(f)-w_C C(f)-w_H H(f)
\]

where \(I\)=information gain, \(T\)=thermal alignment, \(C\)=known travel cost, \(H\)=hazard/risk.

### INVESTIGATE

- Trigger on nontrivial heat/person clue.
- Reduce traversal speed/distance; prefer scan and safe viewpoints.
- Request a second observation from a different viewpoint if evidence is uncertain.

### CONFIRM

Require multimodal persistence; a thermal hotspot alone is never enough.

Example local confirmation score:

\[
C_{person}=0.45C_{thermal}+0.40C_{RGB}+0.15C_{persistence}
\]

Example confirmation gate:

```text
Accept candidate only if:
- Gemini survivor_assessment is CONFIRMED_CANDIDATE
- thermal evidence >= 0.65
- RGB person evidence >= 0.50
- evidence persists across >= 2 observations
- local confidence/score >= required threshold
```

Include decoys: warm rock, campfire, animal, or reflective object.

### RESCUE

- Local code computes shortest safe known route to candidate/survivor node.
- Gemini may choose scan/approach/stop actions at final approach.
- Mark survivor secured once rover reaches the valid rescue range.

### EXTRACT

- Compute shortest safe route from current node to base/extraction via Dijkstra/A* over `safe` edges.
- Gemini can issue `RETURN_TO_BASE`; deterministic executor follows graph route.
- Complete at base; show rescue metrics.

## 8. Gemini Input

One multimodal Gemini request per decision event. Send **both images in the same request** so the model can jointly reason across RGB and thermal; include a compact authoritative text/JSON summary for geometry and graph memory.

### Permanent instruction

```text
You are the high-level decision agent for a simulated search-and-rescue rover.
Mission priority: locate, confirm, rescue, and extract a missing person while preserving a safe route to base.

You receive aligned RGB and thermal images, local geometry, and a compact topological map summary.
Geometry and legal candidates are authoritative. You cannot see the full terrain.
Treat thermal evidence alone as a lead, not confirmation. Prefer safe unexplored routes during search. Investigate conflicting evidence cautiously from safe viewpoints.
Choose exactly one candidate/action listed in the input. Return JSON only matching the response schema. Keep the reason to one sentence.
```

## 9. Gemini Output

Gemini returns a single candidate selection plus semantic assessment. It does not output raw motor values, full trajectories, or arbitrary unvalidated coordinates.

```json
{
  "choice_id": "E17",
  "intent": "INVESTIGATE_THERMAL_LEAD",
  "survivor_assessment": "POSSIBLE",
  "confidence": 0.76,
  "brief_reason": "The known safe eastern route aligns with the strongest recurring thermal evidence."
}
```

Allowed values:

```text
intent:
EXPLORE_FRONTIER | FOLLOW_KNOWN_ROUTE | INVESTIGATE_THERMAL_LEAD |
SCAN | APPROACH_CANDIDATE | MARK_SURVIVOR | RETURN_TO_BASE

survivor_assessment:
NO_EVIDENCE | POSSIBLE | LIKELY | CONFIRMED_CANDIDATE
```

Validation rules:

```text
- choice_id must be one of the supplied candidates.
- intent must be compatible with current mission phase.
- MARK_SURVIVOR requires local confirmation gate to pass.
- RETURN_TO_BASE is allowed only after rescue/secure state.
- Invalid/missing output: default to safe SCAN or request retry.
- Gemini rationale is UI-only; execution relies on validated choice ID.
```

## 10. Local Planning and Backtracking

Known graph routing uses Dijkstra or A* over verified `safe` edges.

\[
\operatorname{path}(u,v)=\arg\min_{p}\sum_{e\in p}\operatorname{cost}(e)
\]

Example edge cost:

\[
\operatorname{cost}(e)=d_e+\lambda_h h_e+\lambda_r r_e
\]

- \(d_e\): length
- \(h_e\): hazard penalty
- \(r_e\): low-clearance/risk penalty

Backtracking is not a Gemini turn-by-turn task:

```text
Current N12; selected frontier originates at N7
Local planner: N12 → N9 → N7
Traverse those known safe edges automatically
At N7, traverse the selected frontier until next meaningful event
```

This is why long corridors compress well: a corridor with several turns is one edge, and an entire known route can be traversed without repeated LLM calls.

## 11. UI and Demo Requirements

Show enough state to make the agent’s role obvious:

1. Third-person Three.js view: rover, terrain, hazards, base, fog.
2. RGB rover camera frame.
3. Aligned thermal frame.
4. Small topological map: visited nodes, safe edges, unexplored frontiers, current node, return route.
5. Agent panel: phase, chosen candidate, survivor assessment, confidence, one-line reason.
6. Metrics: time/steps, nodes explored, thermal leads investigated, safe return route status, rescue result.

Recommended scenario:

- One actual survivor
- One or two thermal decoys
- Several branches/dead ends
- A fixed random seed for reliable judging replay
- A procedural seed selector for live novelty

## 12. Performance and Call Budget

- Render/animation: ~30–60 FPS.
- Raycast/local safety: each local update/frame as needed.
- Gemini: only at nodes, intersections, new evidence, blocked traversal, or mission transitions.
- Target: approximately 10–25 Gemini decisions per complete mission, not hundreds.
- Send images at meaningful decisions; do not call the model every physics tick.
- Keep map state external and compact; never rely on context history for exact geometry.

## 13. Minimal Build Order

1. Create world, rover, base, survivor, obstacles, and deterministic node graph.
2. Implement graph traversal and Dijkstra/A*; prove search/rescue works without Gemini.
3. Add RGB/thermal camera passes and LiDAR raycast summary.
4. Add graph/frontier discovery/update behavior.
5. Call Gemini with images + compact packet; constrain structured output to candidate choice.
6. Add validation, fallback `SCAN`, timeout/retry, and graph-state logging.
7. Add UI panels and rescue-state visual payoff.
8. Save a successful seeded mission/replay for demo resilience.

## 14. Honest Project Claim

> Gemini jointly interprets rover RGB and thermal imagery with live geometric constraints and a sparse topological memory to choose which safe route or unexplored frontier to pursue. Deterministic mapping and path-planning code maintains the map, validates movement, and guarantees safe backtracking and extraction.

This is a multimodal, partially observable search-and-rescue agent—not a claim that Gemini independently performs SLAM, continuous motor control, or online reinforcement learning.
